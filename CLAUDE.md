# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

FoodTracker — a Kotlin Multiplatform grocery/expiration-date tracker with a Jetpack Compose Android app and a native SwiftUI iOS app. Pantry data persists on-device only, via a local database on each platform (Room on Android, SwiftData on iOS — see "Data layer" below); there is no sync of the pantry between devices or platforms. The one backend is for the Recipe tab's paid route: Cloud Functions in `functions/` with Firestore, Firebase Auth (anonymous, Google, and Apple on iOS only) and App Check, in the Firebase project `bestbefore-f9ee1` (see "Recipe" below). Nobody reaches it until they start a purchase, and the free recipe routes never do. Crashlytics ("Crash reporting" below) is the other Firebase product. Barcodes are scanned (CameraX + ML Kit on Android), looked up against the Open Food Facts API, and expiration dates are extracted either from GS1 Application Identifiers in the barcode itself or via on-device OCR of the printed date (ML Kit Text Recognition on Android, Apple Vision on iOS).

## Commands

Requires JDK 17. Modules: `:shared` (KMP), `:androidApp`.

```bash
./gradlew :shared:testAndroidHostTest                       # shared-module commonTest, run on the JVM (`:shared:test` does not exist)
./gradlew :androidApp:testDebugUnitTest                      # androidApp unit tests (includes Room DAO tests, via Robolectric)
./gradlew :androidApp:testDebugUnitTest --tests "*ClassName*"  # single test class
./gradlew :androidApp:assembleDebug                        # build Android debug APK
./gradlew :androidApp:installDebug                         # build + install on connected device/emulator
xcodebuild -project iosApp/FoodTracker.xcodeproj -scheme FoodTracker \
  -destination 'generic/platform=iOS Simulator' build      # build iOS app
cd functions && npm ci && npm run lint && npm run typecheck  # backend (Node.js 24)
cd functions && npm test                                    # backend tests (Vitest) against the Auth + Firestore emulators, project demo-foodtracker; needs Java 21+
./gradlew :androidApp:installDebug -PrecipeEmulatorHost=10.0.2.2  # debug build against the local emulators (functions/README.md, "Running the functions for the apps")
```

Every backend test needs the emulators, so there is no separate unit-test script. CI (`.github/workflows/ci.yml`, job `functions`) lints, typechecks, builds and runs the emulator tests on changes under `functions/`; nothing deploys the backend automatically (`functions/README.md`, "Deploying from CI").

**Releases** are cut with `scripts/release`, not by pushing to main: it bumps the version in `Version.xcconfig` (the single version of both apps: `androidApp/build.gradle.kts` reads it for `versionName`, and it is the Xcode project's base configuration, so no target sets `MARKETING_VERSION` itself) on a `release/vX.Y.Z` branch and writes `release-notes/vX.Y.Z/<play-locale>.txt`. CI (`.github/workflows/ci.yml`) publishes pushes to `release/v*` to Play internal and TestFlight, and on the PR's merge promotes that build to Play closed testing, applies the Play listing (`scripts/play_listing.py --images --apply`), sets the App Store listing and screenshots and submits the newest TestFlight build of the version for App Store review (`scripts/testflight.py appstore --screenshots`; a listing that can't be applied in full stops the submission), and tags `vX.Y.Z`. Main publishes nothing. See "Releasing" in README.md.

**Store listings** live in `store-listing/` and reach the stores only through that release flow; don't paste them in the consoles by hand. The iPhone Duo screenshots and the App Store header/search-result images go through the App Asset Library (`sync_placements` in `scripts/testflight.py`), the other screenshot sets through `appScreenshotSets`; `scripts/testflight.py screenshots --inspect` prints, read-only, what App Store Connect holds. `scripts/check_store_listing.py` gates both syncs. Dry runs: `scripts/testflight.py listing`, `scripts/testflight.py screenshots`, `scripts/play_listing.py --images` (each writes only with `--apply`); offline tests: `python3 -m unittest discover -s scripts/tests` (CI job `scripts`).

The Firebase configs are committed (`androidApp/google-services.json`, `iosApp/FoodTracker/GoogleService-Info.plist`); building and running the app needs no other external setup. The backend's one-time console setup (what is done on the live project and what is left) is the owner's checklist in `docs/recipe-setup.md`. See "Data layer" below for what actually persists where.

## Architecture

**iOS does not consume the `shared` KMP module.** Despite the module existing and building an `iosArm64`/`iosSimulatorArm64`/`iosX64` framework (`SharedApp`), nothing under `iosApp/` links or imports it — there is no `SharedApp` reference anywhere in the Xcode project or Swift sources. iOS is a fully independent, parallel reimplementation:

- `iosApp/FoodTracker/Models/LocalModels.swift` — Swift structs mirroring `shared`'s domain models (`PantryItem`, `StorageLocation`, `ProductInfo`), not generated from or bound to them.
- `iosApp/FoodTracker/ViewModels/NativePantryViewModel.swift` — reimplements the filtering/counting logic from `PantryStateHolder.kt` by hand, calls the Open Food Facts REST API directly with `URLSession` (bypassing the shared Ktor client and its `OpenFoodFactsApi`) — no GS1 barcode parsing, no shared `ExpiryNotificationCalculator` (it schedules local notifications itself via `IOSNotificationManager`).

**Practical implication:** a change to domain logic, parsing rules, or notification timing in `shared/` (GS1 parsing, date-OCR heuristics, expiry-status thresholds, notification scheduling) has no effect on iOS and must be ported to the corresponding Swift file by hand if iOS behavior should match. Don't assume "shared" code is shared with iOS — verify by grepping `iosApp/` before relying on it.

**Data layer**: Android and iOS each persist locally through their own platform database — there is no shared schema or sync between them, consistent with iOS not consuming `shared` (above).

- Android: `PantryRepository` is a platform-agnostic interface in `shared/.../repository/`. Its only implementation is `RoomPantryRepository` (`androidApp/.../data/local/`), backed by a Room database (`FoodTrackerDatabase`, `exportSchema = false`). Room lives in `androidApp`, not `shared`, because `shared`'s Android target uses AGP 9's built-in-Kotlin compilation, which KSP (Room's annotation processor) only supports there via `com.google.devtools.ksp` 2.3.1+ using the plain `<kspVersion>` scheme (no `<kotlinVersion>-` prefix) — `androidApp` applies that plugin.
  - **Every schema change ships with a real `Migration`** (`MIGRATION_<old>_<new>` in `FoodTrackerDatabase`, registered in `AppModule`'s `addMigrations` and in every `FoodTrackerMigrationTest` builder, with a test that asserts the upgraded rows). Never bump `version` alone, and never use `fallbackToDestructiveMigration`. The pantry is the user's only copy of their data, so an upgrade must never wipe it. The only exception is when the user explicitly asks, in the current session, to skip the migration.
  - The database is at `version = 14`; `MIGRATION_13_14` added the `saved_recipes` table (saved recipes and menus: a `kind` column and a JSON payload).
  - On iOS, the equivalent rule is: a new stored property on a SwiftData `@Model` (e.g. `PantryItemRecord`, `SavedRecipeRecord`) needs a default value so the store migrates in place, and a new `@Model` goes into the `Schema` in `NativePantryViewModel.sharedModelContainer`.
- iOS: `NativePantryViewModel` persists through SwiftData. `PantryItemRecord` (`iosApp/FoodTracker/Models/PantryItemRecord.swift`) is the `@Model` class Room's `PantryItemEntity` doesn't have a counterpart for elsewhere — the view model converts to/from the plain `PantryItem` struct on every read/write (`asPantryItem` / `init(from:)` / `update(from:)`) so the rest of `iosApp/` keeps working with `PantryItem` unchanged. The `ModelContainer` is a `nonisolated static let` (`NativePantryViewModel.sharedModelContainer`) so it can be used as a default-argument value from a `@MainActor` init without a Swift 6 isolation error.
- There used to be a Firestore-backed pantry and matching iOS Firebase integration; both were removed and the pantry should not be moved to a server or synced without being asked. The recipe backend's Firestore is unrelated: it is reached only by the Cloud Functions through the Admin SDK (`firestore.rules` denies every client read and write), and the apps do not link the Firestore SDK. Pantry data leaves the phone only as the ticked items (name, date, quantity) plus recipe settings and the allergen list in a paid `generateRecipe` call. The allergen list is health data (GDPR Art. 9): it is sent only after the consent step (`shared/.../recipe/AllergenConsent.kt`, iOS `AllergenConsent` in `Recipe/RecipeWire.swift`, same rules and wording on both; raise `ALLERGEN_CONSENT_VERSION` / `AllergenConsent.version` when the wording changes), with `allergenConsent: true`, and the server refuses allergens without it (`ALLERGEN_CONSENT_REQUIRED`). Without consent the server route is blocked while allergens are set; never send a request with the allergens left out instead. Crashlytics sends crash reports only, never pantry data.

**Crash reporting**: Firebase Crashlytics on both platforms, in the Firebase project `bestbefore-f9ee1`. No Analytics, and no Firestore SDK in the apps; the other Firebase products the apps link (Auth, Functions, App Check) are only for the Recipe paid route.

- Android: the `com.google.gms.google-services` and `com.google.firebase.crashlytics` plugins in `androidApp`; the latter uploads the R8 mapping on release builds. Collection is off in debug builds through the `firebase_crashlytics_collection_enabled` manifest meta-data (`manifestPlaceholders["crashlyticsCollectionEnabled"]`). Don't call `setCrashlyticsCollectionEnabled` in code: its value persists on the device and would override the manifest.
- iOS: the `FirebaseCrashlytics` Swift package (pinned in `project.xcworkspace/xcshareddata/swiftpm/Package.resolved`, the one workspace file `.gitignore` lets through). `FoodTrackerApp.init` calls `FirebaseBootstrap.configure()` (`iosApp/FoodTracker/Recipe/FirebaseBootstrap.swift`) in every build, Debug included, because the paid route needs Firebase there too (App Check debug provider, the emulators). Collection stays off in Debug through the `FirebaseCrashlyticsCollectionEnabled` Info.plist key, set from the `CRASHLYTICS_COLLECTION_ENABLED` build setting (`NO` in Debug); as on Android, never `setCrashlyticsCollectionEnabled`. The "Upload Crashlytics dSYMs" run-script phase skips Debug. `FirebaseAppCheckTokenAutoRefreshEnabled` is `false` in Info.plist so configuring creates no App Check token. The widget extension doesn't link Firebase.

**Recipe** (replaces the old Calendar tab; design in `docs/design/`, decisions in `docs/design/brief.md`). Three routes write a recipe from the ticked pantry items and a `RecipeConfig`: the shared prompt (free, copied or shared to another app), the phone's own model (free: Gemini Nano through ML Kit GenAI Prompt API on Android, Apple Foundation Models on iOS 26+ behind `#available`), and the server (packs of 10 / 50 / 100 recipes, `recipes_10` / `recipes_50` / `recipes_100`; a 3-day menu is server-only). The unit people buy is called a "recipe" in all user-facing text, never a credit or token (the backend's code and docs say "credits"; that word never reaches the UI).

- **Costs are never hard-coded.** What a recipe and a 2- or 3-course menu take comes from the server (`costs` beside every `balance`, from `config/runtime.costs`; default 1 / 4 / 5). The clients cache the last table and fall back to 1 / 4 / 5 only before they have received one (`RecipeCosts.fallback` on iOS); the server's own check decides.
- Android: `RecipeStateHolder` (`shared/.../recipe/`, separate from `PantryStateHolder`, which it reads items from) owns the tab's state; the paid route's logic is `RecipePaid` in the same package. Its seams are plain interfaces: `RecipeConfigRepository`, `SavedRecipeRepository`, `OnDeviceRecipeModel` (`RecipeServices.kt`), and for the paid route `RecipeBackend`, `RecipeStore`, `RecipeAccount`, `RecipePaidRepository` (`RecipePaidServices.kt`). Implementations live in `androidApp/.../recipe/` (`GeminiNanoRecipeModel`; `paid/`: `FirebaseRecipeBackend`, `PlayRecipeStore` on Play Billing, `FirebaseRecipeAccount` with Credential Manager for Google, `RecipeFirebase`), `data/local/RoomSavedRecipeRepository` and `settings/`. Screens: `ui/screens/Recipe*.kt`, `SavedRecipesScreen.kt`.
- **Android signs in with Google only** (owner's decision, 2026-11-14): Apple's guidelines allow a custom Sign in with Apple button on Android only with Apple's logo artwork, which can't be redistributed in this public repository, and allow no logo-less button. iOS keeps Apple and Google. An account can still carry Apple (made on an iPhone, Google added there): Android shows its providers by name, offers no "add Apple", re-authenticates for deletion with Google, and sends no Apple code: the server revokes the Apple refresh token it stored from the account's last Apple sign-in on an iPhone (iOS sends every Apple sign-in's authorization code to `registerAppleSignIn`, quietly; the token is kept envelope-encrypted with a Cloud KMS key, `functions/README.md` "Stored Sign in with Apple tokens"). Only when `deleteAccount` answers `appleLinkRemoved: false` do the apps tell the person to turn off Sign in with Apple for the app in the Apple Account settings; never warn up front. Never log, return or store an Apple code or token outside `users/{uid}.appleToken`, and keep it off every tombstone. Where Android offers sign-in it tells someone signed in with Apple on an iPhone to add Google there first. Don't reintroduce an Apple button or `OAuthProvider("apple.com")` on Android, and keep `LarderIcons.Apple` (the fruit category uses it).
- Android paid-route gate: `recipePaidRouteBuildAllowed` (`paid/RecipeFirebase.kt`), checked in `AppModule`. Release builds get the Firebase/Play implementations only when installed from Google Play (Play Integrity); otherwise the `NotAvailable*` / `NoRecipeAccount` stand-ins are bound and the tab shows only the free routes. **Debug builds always offer it**: against the real project with the App Check debug provider (register the token logcat prints), or, with `-PrecipeEmulatorHost=10.0.2.2`, against the Firebase emulators with an unsigned stand-in App Check token and a fake store whose purchases carry `fake-<pack>-<id>` tokens (`src/debug/.../RecipeBuildVariant.kt`). Either way the route hides itself at run time if App Check refuses the build or the store sells it no pack. `RecipeFirebase` installs App Check and points at the emulators lazily, on first paid use.
- iOS: `RecipeViewModel` (`ViewModels/RecipeViewModel.swift`) is the hand port of `RecipeStateHolder`; `RecipeCredits` (`Recipe/RecipeCredits.swift`) holds the paid route's account, StoreKit 2 purchases and balance. Seams are the protocols in `Recipe/RecipeServices.swift` (`OnDeviceRecipeModel`, `RecipeBackend`, `RecipeConfigStore`, `SavedRecipeStore`); implementations are `FoundationModelsRecipeModel`, `FirebaseRecipeBackend`, `RecipeAccount` (Sign in with Apple with scope `.email` only, GoogleSignIn), `RecipeStoreKit`, `SwiftDataSavedRecipeStore` (`SavedRecipeRecord`). The prompt is `Recipe/RecipePromptBuilder.swift`, a port of `shared`'s `RecipePromptBuilder.kt`. Views are in `Views/Recipe/`. The Buy sheet shows the consumption line ("If you ask Apple for a refund, we tell Apple how many of these recipes you have used."), and only purchases made after it was shown are sent with `consumptionConsent: true`.
- iOS paid-route gate: `RecipeCredits.isPaidRouteAvailable` needs `FirebaseBootstrap.canAttest` (always in Debug, App Attest support in release), no App Check failure so far, and packs offered by the store (or a known balance). Debug builds use the App Check debug provider against the real project; there the scheme's `Recipes.storekit` products buy, but the real server always rejects Xcode-environment transactions, so use a sandbox account. The launch argument `-recipeEmulatorHost 127.0.0.1` points a Debug build at the emulators (stand-in App Check token), whose fake verifier accepts Xcode StoreKit transactions as sandbox.
- Demo launch arguments (Debug only, nothing is sent): iOS `-demoRecipeCredits <n>` with `-demoRecipeState <phone|account|unconfirmed|pending|paused|offline|blocked|otherAccount|busy>`, `-demoRecipeMode menu`, `-demoRecipeCourses 2|3`, `-demoRoute recipeResult|recipeMenu|recipeSettings|savedRecipes`, `-demoAllergen <name>`, plus the general `-demoBackup` / `-demoTab`; Android intent extras `--es demoBackup <path>` and `--es demoTab <tab>` (`MainActivity`). `scripts/ios_screenshots.sh` and `scripts/android_screenshots.sh` use them.
- Purchases and recovery: Play purchases are consumed by the server, never by the client; both clients tie a purchase to the buyer with `UUIDv5(6f2b3c1e-8d4a-4b7e-9c35-2a1f0e7d5b48, uid)` (`setObfuscatedAccountId` / `appAccountToken`). Unconfirmed purchases are resubmitted at launch, when the app comes to the foreground and on "Try now". A generation whose answer was lost is recovered by polling `getGeneration` (App Check token not consumed), never by re-sending `generateRecipe`, which consumes a limited-use token per call. `purchasesBlocked: true` in a response hides buying and nothing else.
- **Name cleaning exists in three places that must stay in step**: the server's rules, `functions/src/core/inputSafety.ts` (authoritative, described in CONTRACT.md "Name rules"); `shared/.../recipe/RecipeWireName.kt` (`cleanWireName`, `cleanAllergenName`); and iOS `RecipeWire.cleanName` in `Recipe/RecipeWire.swift`. Names are accepted in any script (letters, marks and digits of every script; look-alike mixing is checked only between Latin, Cyrillic and Greek). All three are tested against one shared fixture, `functions/test/fixtures/names.json` (real product names in 25 languages plus adversarial inputs, each with the clients' cleaned output and the server's verdicts): the server in `functions/test/nameFixture.test.ts` (part of `npm test`); Android in `shared/src/androidHostTest/.../ServerNameRuleTest.kt` (`./gradlew :shared:testAndroidHostTest`), which also ports the server's normaliser line by line and must reproduce its verdicts; iOS with `iosApp/NameFixtureCheck/check.sh`, which compiles the name-cleaning section of `RecipeWire.swift` with `swiftc` outside the Xcode project and runs it over the fixture (needs only the Xcode toolchain; not run by CI, so run it after touching `cleanName`). A rule change updates the server, both cleaners, the port and the fixture together. A pantry name the server still refuses is left out and the request retried with a new `requestId`; an allergen is never sent shortened and a refused one stops the request.
- Backend: `functions/` (TypeScript, Cloud Functions 2nd gen, region `europe-west1`); layout, money and refund rules, spend ceilings, prompt-injection defences, logs to alert on, parameters and local running in `functions/README.md`. The wire contract is `functions/CONTRACT.md`, with `functions/src/contract.ts` as the source of truth; the client mirrors are `shared/.../recipe/RecipePaidServices.kt` + `androidApp/.../recipe/paid/FirebaseRecipeBackend.kt` and `iosApp/FoodTracker/Recipe/RecipeWire.swift`. Change all of them together.
- **Never delete `purchases/{id}` or `buyers/{key}` documents.** A purchase document is the only replay guard against redeeming one store purchase twice (account deletion sets its `uid` to null and keeps `formerUid`); a buyer document is the refund-after-use record behind `purchasesBlocked` (unblock with `blockedOverride` on it, never by deleting it). Likewise `users/{uid}` tombstones (`deletedAt`, `mergedInto`) stay, because every transaction checks them and refunds follow `mergedInto`.
- A balance goes up only through a store-verified purchase whose `purchases/` document didn't exist yet. App Check is rate reduction, not the money guard.
- Failures are refunded or charged by the server's rules (README "How the money works"); the UI never promises a refund. Its reasons map to fixed wording: `GENERATION_DISABLED` shows "Recipes from packs are paused", `USER_DAILY_LIMIT` and `DAILY_CAP` "That's the limit for today", `INFRA_FAILURE_LIMIT` "We're having trouble writing recipes right now", each saying no recipes were taken.
- The server clears Google's name and photo from the Firebase Auth user after sign-in; clients must not read or store `displayName` / `photoURL`.
- Configuration and saved recipes stay on the device (Android: `AndroidRecipeConfigRepository` under its own key, outside `AppSettings`, and the `saved_recipes` table; iOS: `UserDefaultsRecipeConfigStore` and `SavedRecipeRecord`), so the backup format and iOS `WireSettings` don't include them.

**Rating prompt**: the OS's own store-rating prompt only (Play In-App Review, `com.google.android.play:review`; iOS `@Environment(\.requestReview)`). No pre-question, no "Rate us" button, no analytics. One rule on both platforms, kept in step by hand: Android `shared/.../review/ReviewPromptRule.kt` + `ReviewPrompter.kt` (tests in `shared/src/commonTest/.../review/`), iOS `iosApp/FoodTracker/Settings/ReviewPrompt.swift` (checked by `iosApp/ReviewPromptCheck/check.sh`, swiftc only, not run by CI). A change to the rule changes both and both tests.

- Asked only after a positive moment: the 3rd or later "Use one" on an item not past its date (on the date counts), or leaving a recipe/menu that was just written (any route; asked on leaving, never over it as it appears).
- And only when: at least 7 days since the first launch (Android: the install time if earlier), at least 2 items in the pantry at once ever, not in a session that showed onboarding, an error (lookup offline), a failed or refused generation, a purchase or account problem, a refused permission (camera, notifications, location), or a demo launch (Android `demoBackup`/`demoTab` extras, iOS any `-demo…` argument); at most once per app version and 120 days apart. A request is recorded only when the OS was asked.
- Counters live under their own key, outside `AppSettings`, so backups and `WireSettings` never carry them: Android `AndroidReviewPromptStore` (`review_prompt` in `foodtracker_settings`), iOS `UserDefaultsReviewPromptStore` (`com.foodtracker.review_prompt` in `.standard`).
- Android seam: `StoreReviewRequester` in shared; `storeReviewRequester()` (`androidApp/.../review/`) gives Play's flow only to release builds installed from Play, a logcat-only stand-in to debug builds, and nothing to other builds. Failures are swallowed. Hooks: `FoodTrackerRoot` (Use one, route changes), `RecipeScreen` / `RecipePaidOverlays` (events, through `LocalReviewPrompter`), `MainActivity.observeForReviewPrompt` (lasting states), `ScannerScreen` (camera refused).
- iOS hooks: `RootTabView.useOne` and onboarding, `RecipeView`'s `path` change (leaving the result), `RecipeViewModel` (`recipeArrived`, `failure` didSet), `RecipeCredits` (problem didSets), `NativePantryViewModel` (`items`, `lookupResult`), `ScannerSheetView`, `IOSNotificationManager`, `StoreGeofenceManager` (refusals). `ReviewPrompt.swift` is also in the widget target, because that target compiles `NativePantryViewModel`.

**DI**: Koin, wired in `androidApp/.../di/AppModule.kt` (`appModule`) and started in `FoodTrackerApp.onCreate`. `MainActivity` resolves `PantryStateHolder` via `by inject()`. The `shared` module itself has no Koin dependency — `PantryStateHolder`'s constructor just takes plain interface params, so it stays constructible on iOS (if iOS ever adopts `shared`) without pulling in an Android-only DI graph.

**State**: on Android, `PantryStateHolder` (in `shared`, platform-agnostic) exposes a single `PantryUiState` via `StateFlow`, driven by collecting `PantryRepository.getItemsFlow()`. Filtering/search/location/status-filter state is applied client-side in `computeFiltered`, not pushed to the repository. Scan flow (barcode → GS1 date extraction → Open Food Facts lookup → optional OCR date override) is also modeled as fields on this same state object rather than a separate view model.

**Barcode/OCR pipeline** (Android): `androidApp/.../camera/BarcodeAnalyzer.kt` and `TextOcrAnalyzer.kt` are CameraX `ImageAnalysis.Analyzer` implementations feeding ML Kit. A scanned barcode first goes through `GS1BarcodeParser.extractExpiryDate` (shared module) to try to pull an expiry date straight out of AI(17)/AI(15) segments before falling back to product lookup + manual/OCR date entry. `DateOcrParser.parseBestDate` (shared module) scores multiple date-format regexes per OCR line, preferring lines near a keyword (EXP, BB, BEST BEFORE, etc.) and multilingual month names.

**Data layer conventions**: shared domain models live under `shared/.../model/`.
