# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

FoodTracker — a Kotlin Multiplatform grocery/expiration-date tracker with a Jetpack Compose Android app and a native SwiftUI iOS app. Pantry data persists on-device only, via a local database on each platform (Room on Android, SwiftData on iOS — see "Data layer" below); there is no sync of the pantry between devices or platforms. The one backend is for the Recipe tab's paid route: Cloud Functions in `functions/` with Firestore, Firebase Auth (anonymous, Google, and Apple on iOS only) and App Check, in the Firebase project `bestbefore-f9ee1` (see "Recipe" below). Nobody reaches it until they sign in or start a purchase, with one exception that carries nothing about the person: the app asks how many free recipes are on offer for signing in (`getWelcomeOffer`, "Free recipes for signing in" below); the free recipe routes never reach it. Crashlytics ("Crash reporting" below) is the other Firebase product. Barcodes are scanned (CameraX + ML Kit on Android), looked up against the Open Food Facts API, and expiration dates are extracted either from GS1 Application Identifiers in the barcode itself or via on-device OCR of the printed date (ML Kit Text Recognition on Android, Apple Vision on iOS).

## Commands

Requires JDK 17. Modules: `:shared` (KMP), `:androidApp`.

```bash
./gradlew :shared:testAndroidHostTest                       # shared-module commonTest, run on the JVM (`:shared:test` does not exist)
./gradlew :androidApp:testDebugUnitTest                      # androidApp unit tests (includes Room DAO tests, via Robolectric)
./gradlew :androidApp:testDebugUnitTest --tests "*ClassName*"  # single test class
./gradlew :androidApp:assembleDebug                        # build Android debug APK
./gradlew :androidApp:installDebug                         # build + install on connected device/emulator
xcodebuild -project iosApp/FoodTracker.xcodeproj -scheme FoodTracker \
  -destination 'generic/platform=iOS Simulator' build      # build iOS app
cd functions && npm ci && npm run lint && npm run typecheck  # backend (Node.js 24)
cd functions && npm test                                    # backend tests (Vitest) against the Auth + Firestore emulators, project demo-foodtracker; needs Java 21+
./gradlew :androidApp:installDebug -PrecipeEmulatorHost=10.0.2.2  # debug build against the local emulators (functions/README.md, "Running the functions for the apps")
scripts/ui_check.sh                                         # UI screenshot check: every Android screen against its baseline (0 none / 1 differences / 2 failed)
scripts/ui_check.sh --record                                # accept the current Android UI as the new baseline
```

**UI screenshot check** (README "UI screenshot check"): Roborazzi on Robolectric renders every `@Preview` under `androidApp/.../ui/` (found by Roborazzi's generated `RoborazziPreviewParameterizedTests` through `FoodTrackerPreviewTester`, which adds a `_NIGHT` twin to previews without a dark variant, pins the clock and compares strictly) plus `ScreenScreenshotTest` (Home, shopping list, add/edit over in-memory fakes), against the PNGs in `androidApp/src/test/snapshots/images/`, recorded on macOS; CI never verifies against them (Robolectric's rendering can differ slightly on Linux): its plain `testDebugUnitTest` renders them, and on a pull request touching Android the `ui-screenshots` jobs in `ci.yml` render the PR's base and head on Linux, compare the two and keep one comment on the PR with what changed (`scripts/ui_diff.py`; images on the `screenshot-diffs` branch, removed when the PR closes; it informs and never fails on a difference). A UI change you mean ships with `--record`ed images; a new `@Preview` needs one too, and its sample data must use fixed dates, never `DateUtils.today()`. Not `scripts/screenshot_check.py`, the slower emulator/simulator check of the store screenshots.

Every backend test needs the emulators, so there is no separate unit-test script. CI (`.github/workflows/ci.yml`, job `functions`) lints, typechecks, builds and runs the emulator tests on changes under `functions/`; nothing deploys the backend automatically (`functions/README.md`, "Deploying from CI").

**Releases** are cut with `scripts/release`, not by pushing to main: it bumps the version in `Version.xcconfig` (the single version of both apps: `androidApp/build.gradle.kts` reads it for `versionName`, and it is the Xcode project's base configuration, so no target sets `MARKETING_VERSION` itself) on a `release/vX.Y.Z` branch and writes `release-notes/vX.Y.Z/<play-locale>.txt`. CI (`.github/workflows/ci.yml`) publishes pushes to `release/v*` to Play internal and TestFlight, and on the PR's merge promotes that build to Play closed testing, applies the Play listing (`scripts/play_listing.py --images --apply`), sets the App Store listing, screenshots and App Review notes (`store-listing/app-store/review-notes.txt`) and submits the newest TestFlight build of the version for App Store review together with the in-app purchases still to be reviewed (`scripts/testflight.py appstore --screenshots`; a listing that can't be applied in full, or purchases App Store Connect won't add to the submission, stop the submission; `scripts/testflight.py iaps` shows the plan read-only; after a rejection it reuses the rejected version and its sent-back submission, marks the rejected items it ships again resolved and resubmits, and when App Store Connect refuses that the fallback is "Resubmit to App Review" on the website, with no re-run needed: `store-listing/app-store/README.md`, "After a rejection"), and tags `vX.Y.Z`. Main publishes nothing. See "Releasing" in README.md.

**Store listings** live in `store-listing/` and reach the stores only through that release flow; don't paste them in the consoles by hand. The iPhone Duo screenshots and the App Store header/search-result images go through the App Asset Library (`sync_placements` in `scripts/testflight.py`), the other screenshot sets through `appScreenshotSets`; `scripts/testflight.py screenshots --inspect` prints, read-only, what App Store Connect holds. `scripts/check_store_listing.py` gates both syncs. On the App Store, an English locale folder other than `en-GB/` may hold only some files and takes en-GB's for the rest (texts, screenshots, header art); `en-AU/` and `en-CA/` hold only `keywords.txt` (`store-listing/app-store/README.md`, "Australia and Canada"). `es-MX/` and `fr-CA/` fall back the same way to `es-ES/` and `fr-FR/` (`fallback()` in `testflight.py`; their screenshot sets are uploaded from the parent folder, since App Store Connect would otherwise show the English ones); no other language falls back. Each App Store localization's privacy policy URL is its language's page on the policy site (`<locale>/privacy_url.txt`, synced with the name and subtitle on the app info); the sync sets a page only once it answers 200 and sets the language chooser root meanwhile (`live_privacy_url`), and Play keeps one app-wide URL, the chooser root, which its API doesn't expose (`store-listing/app-store/README.md`, "Privacy policy URL per language"). Play has no text fallback and deliberately no en-AU/en-CA listings; only its images fall back, es-419 and fr-CA to es-ES and fr-FR (`IMAGE_FALLBACKS` in `play_listing.py`). Dry runs: `scripts/testflight.py listing` (texts and App Review notes), `scripts/testflight.py screenshots`, `scripts/play_listing.py --images` (each writes only with `--apply`), and `scripts/testflight.py iaps` (read-only); offline tests: `python3 -m unittest discover -s scripts/tests` (CI job `scripts`). `scripts/screenshot_check.py` re-takes every raw screenshot through the two capture scripts, one device at a time, and compares them with a local baseline in `build/screenshot-check/` with reg-cli (exit 0 none / 1 differences / 2 failed or no baseline; short summary on stdout, the rest in its `run.log`; README "Screenshot check").

The Firebase configs are committed (`androidApp/google-services.json`, `iosApp/FoodTracker/GoogleService-Info.plist`); building and running the app needs no other external setup. The backend's one-time console setup (what is done on the live project and what is left) is the owner's checklist in `docs/recipe-setup.md`. See "Data layer" below for what actually persists where.

**App languages**: en (en-GB is the stores' primary), ru, nb, es, de, fr, sv, da, on both platforms (Android `values-<code>/strings.xml`, iOS `<code>.lproj/` registered in `project.pbxproj`'s `knownRegions` and the three variant groups, which the app and the widget share). ## Architecture

**iOS does not consume the `shared` KMP module.** Despite the module existing and building an `iosArm64`/`iosSimulatorArm64`/`iosX64` framework (`SharedApp`), nothing under `iosApp/` links or imports it — there is no `SharedApp` reference anywhere in the Xcode project or Swift sources. iOS is a fully independent, parallel reimplementation:

- `iosApp/FoodTracker/Models/LocalModels.swift` — Swift structs mirroring `shared`'s domain models (`PantryItem`, `StorageLocation`, `ProductInfo`), not generated from or bound to them.
- `iosApp/FoodTracker/ViewModels/NativePantryViewModel.swift` — reimplements the filtering/counting logic from `PantryStateHolder.kt` by hand, calls the Open Food Facts REST API directly with `URLSession` (bypassing the shared Ktor client and its `OpenFoodFactsApi`) — no GS1 barcode parsing, no shared `ExpiryNotificationCalculator` (it schedules local notifications itself via `IOSNotificationManager`).

**Open Food Facts**: requests to it carry `BestBefore-Android/<versionName> (https://github.com/daniil-pastuhov/FoodTrack)` / `BestBefore-iOS/<CFBundleShortVersionString> (…)` as their User-Agent, never an email address (`openFoodFactsUserAgent`, passed to `OpenFoodFactsApi` from `AppModule`; iOS `OpenFoodFacts.userAgent`). Pictures carry it only on Open Food Facts' hosts (`isOpenFoodFactsHost`: Coil's `ImageLoader` from `FoodTrackerApp.newImageLoader`; iOS `ProductImageView`). A 429 is `ProductLookupResult.Busy` / `LookupResult.busy`: the offline panel's choices with "Open Food Facts is busy" instead of "You're offline". The product sheet's credit line (Open Food Facts and the ODbL / CC BY-SA licences) shows for every item whose picture is on an Open Food Facts host or whose product has nutrition data (`isFromOpenFoodFacts` / `OpenFoodFacts.isSource`; nothing records where a typed name came from) and opens the product's page there (`openFoodFactsPageUrl`, the site without a barcode).

**Links into the app**: iOS opens `foodtracker://<name>` (`AppRoute(externalName:)` in `AppRouter.swift`, also the quick actions' names): `home`, `recipe` (the Recipe tab, as if tapped; the App Store's in-app event uses it), `shopping-list`, `scan`, `add-item`. During first run only a tab link is kept, and opened when onboarding ends on Home. Android declares no URL scheme: its widgets and shortcuts use intent extras (`MainActivity`).

**Permission requests (iOS, App Review guideline 5.1.1(iv); 2.1.0 was rejected for it)**: a screen that explains a permission before the system prompt has one button, worded neutrally (`continue_button`, "Continue"; never "Allow…", "Turn on…", "Enable…"), which always puts the system prompt up, and no way past it without the prompt (no Not now, skip, close or Back): onboarding's notifications and camera steps (`OnboardingView`, `OnboardingFlow.canGoBack`), and the "not asked yet" reminders notes on Home (not closable while not asked) and in Settings, reachable only after Not now in an older version's onboarding or a failed request. The flow goes on whatever the answer; a refusal is met where the feature is used with a link to the Settings app (Home's reminders note, the scanner's "The camera is off"). Asking in context with no explanation first (the scanner, "Save my current location", the Always escalation after a shop is saved) needs no such screen. Android's onboarding keeps Not now and Back.

**Practical implication:** a change to domain logic, parsing rules, or notification timing in `shared/` (GS1 parsing, date-OCR heuristics, expiry-status thresholds, notification scheduling) has no effect on iOS and must be ported to the corresponding Swift file by hand if iOS behavior should match. Don't assume "shared" code is shared with iOS — verify by grepping `iosApp/` before relying on it.

**Data layer**: Android and iOS each persist locally through their own platform database — there is no shared schema or sync between them, consistent with iOS not consuming `shared` (above).

- Android: `PantryRepository` is a platform-agnostic interface in `shared/.../repository/`. Its only implementation is `RoomPantryRepository` (`androidApp/.../data/local/`), backed by a Room database (`FoodTrackerDatabase`, `exportSchema = false`). Room lives in `androidApp`, not `shared`, because `shared`'s Android target uses AGP 9's built-in-Kotlin compilation, which KSP (Room's annotation processor) only supports there via `com.google.devtools.ksp` 2.3.1+ using the plain `<kspVersion>` scheme (no `<kotlinVersion>-` prefix) — `androidApp` applies that plugin.
  - **Every schema change ships with a real `Migration`** (`MIGRATION_<old>_<new>` in `FoodTrackerDatabase`, registered in `AppModule`'s `addMigrations` and in every `FoodTrackerMigrationTest` builder, with a test that asserts the upgraded rows). Never bump `version` alone, and never use `fallbackToDestructiveMigration`. The pantry is the user's only copy of their data, so an upgrade must never wipe it. The only exception is when the user explicitly asks, in the current session, to skip the migration.
  - The database is at `version = 15`; `MIGRATION_14_15` added the `staples` table (the person's staples: `id`, `name`, `presetId`, `addedAtEpochMillis`), `MIGRATION_13_14` the `saved_recipes` table (saved recipes and menus: a `kind` column and a JSON payload).
  - Recipe pictures are not in Room: Android keeps them as files, `filesDir/recipe_pictures/<savedId>/dish.jpg` and `step-<n>.jpg` (`RecipePictureFiles` / `AndroidRecipePictureStore` in `androidApp/.../recipe/`, behind shared's `RecipePictureStore`), named by optional fields of the payload JSON (`Recipe.requestId` / `picture` / `stepPictures`, `Menu.requestId`; set by the app only, `withoutLocalFields` strips them from anything that arrives), so no schema change. That folder alone is excluded from Auto Backup and device transfer (`res/xml/backup_rules.xml`, `data_extraction_rules.xml`, set in the manifest); a restored row shows without pictures. A deleted row's folder stays (Undo) until the launch sweep removes folders without a row older than 10 minutes. iOS keeps them on `SavedRecipeRecord` (`dishImage` and `stepImages` with `.externalStorage`, `thumbnail`, all nil by default; no new `@Model`).
  - On iOS, the equivalent rule is: a new stored property on a SwiftData `@Model` (e.g. `PantryItemRecord`, `SavedRecipeRecord`) needs a default value so the store migrates in place, and a new `@Model` goes into the `Schema` in `NativePantryViewModel.sharedModelContainer` (`StapleRecord`, the staples, is the latest).
  - Backups (the app's backup file, `BackupDocument` on both platforms, file `version` still 1) carry the pantry and the shopping list, and staples (`staples`, optional, ignored by older versions; a file without it reads as no staples; REPLACE clears and restores at most 20, MERGE adds those that match no existing staple). `clearAllData` stays pantry-only.
- iOS: `NativePantryViewModel` persists through SwiftData. `PantryItemRecord` (`iosApp/FoodTracker/Models/PantryItemRecord.swift`) is the `@Model` class Room's `PantryItemEntity` doesn't have a counterpart for elsewhere — the view model converts to/from the plain `PantryItem` struct on every read/write (`asPantryItem` / `init(from:)` / `update(from:)`) so the rest of `iosApp/` keeps working with `PantryItem` unchanged. The `ModelContainer` is a `nonisolated static let` (`NativePantryViewModel.sharedModelContainer`) so it can be used as a default-argument value from a `@MainActor` init without a Swift 6 isolation error.
- There used to be a Firestore-backed pantry and matching iOS Firebase integration; both were removed and the pantry should not be moved to a server or synced without being asked. The recipe backend's Firestore is unrelated: it is reached only by the Cloud Functions through the Admin SDK (`firestore.rules` denies every client read and write), and the apps do not link the Firestore SDK. Pantry data leaves the phone only as the ticked items (name, date, quantity) plus recipe settings, the allergen list and the names of the person's staples (names only; a staple on the shopping list is left out) in a paid `generateRecipe` call (staples only to a server that says `acceptsStaples`), and, only when the person turns on "Send all products" in Recipe settings (off by default, its description says so plainly), the other pantry items' names, dates and quantities as `optionalIngredients` in that call (and only to a server that says `acceptsOptionalIngredients`). The shared prompt lists the staples too, in text the person sends elsewhere themselves. The allergen list is health data (GDPR Art. 9): it is sent only after the consent step (`shared/.../recipe/AllergenConsent.kt`, iOS `AllergenConsent` in `Recipe/RecipeWire.swift`, same rules and wording on both; raise `ALLERGEN_CONSENT_VERSION` / `AllergenConsent.version` when the wording changes), with `allergenConsent: true`, and the server refuses allergens without it (`ALLERGEN_CONSENT_REQUIRED`). Without consent the server route is blocked while allergens are set; never send a request with the allergens left out instead. A recipe asked with pictures sends nothing more from the phone: the picture prompt is a fixed template around a short English description of the dish that the recipe model writes and the server checks; the server copies nothing the person typed into it, and no allergens, taste answers or account or device identifiers (a product name can still appear in the description, since the recipe model saw the pantry). "Report this recipe" sends the result's `requestId`, a reason and the person's optional note, never recipe text or pantry data (the server copies the result from its own generation). Crashlytics sends crash reports only, never pantry data.

**Crash reporting**: Firebase Crashlytics on both platforms, in the Firebase project `bestbefore-f9ee1`. No Analytics, and no Firestore SDK in the apps; the other Firebase products the apps link (Auth, Functions, App Check) are only for the Recipe paid route.

- Android: the `com.google.gms.google-services` and `com.google.firebase.crashlytics` plugins in `androidApp`; the latter uploads the R8 mapping on release builds. Collection is off in debug builds through the `firebase_crashlytics_collection_enabled` manifest meta-data (`manifestPlaceholders["crashlyticsCollectionEnabled"]`). Don't call `setCrashlyticsCollectionEnabled` in code: its value persists on the device and would override the manifest.
- iOS: the `FirebaseCrashlytics` Swift package (pinned in `project.xcworkspace/xcshareddata/swiftpm/Package.resolved`, the one workspace file `.gitignore` lets through). `FoodTrackerApp.init` calls `FirebaseBootstrap.configure()` (`iosApp/FoodTracker/Recipe/FirebaseBootstrap.swift`) in every build, Debug included, because the paid route needs Firebase there too (App Check debug provider, the emulators). Collection stays off in Debug through the `FirebaseCrashlyticsCollectionEnabled` Info.plist key, set from the `CRASHLYTICS_COLLECTION_ENABLED` build setting (`NO` in Debug); as on Android, never `setCrashlyticsCollectionEnabled`. The "Upload Crashlytics dSYMs" run-script phase skips Debug. `FirebaseAppCheckTokenAutoRefreshEnabled` is `false` in Info.plist so configuring creates no App Check token. The widget extension doesn't link Firebase.

**Recipe** (replaces the old Calendar tab; design in `docs/design/`, decisions in `docs/design/brief.md`). Three routes write a recipe from the ticked pantry items and a `RecipeConfig`: the shared prompt (free, copied or shared to another app), the phone's own model (free: Gemini Nano through ML Kit GenAI Prompt API on Android, Apple Foundation Models on iOS 26+ behind `#available`), and the server (packs of 10 / 50 / 100 recipes, `recipes_10` / `recipes_50` / `recipes_100`; a menu set, 1 to 4 days of 1 to 3 courses, is server-only). The unit people buy is called a "recipe" in all user-facing text, never a credit or token (the backend's code and docs say "credits"; that word never reaches the UI).

- **The phone's model follows the chosen recipe language** (`RecipeUiState.language`: `RecipeConfig.language`, or the app's language for "Same as the app"; never the device's), one rule on both platforms: no model hides the route; a model that doesn't write that language hides it too, ready or still downloading (no "getting ready" callout, no mention in "How recipes work"), and Recipe settings shows one quiet line under the language saying why (`onDeviceLanguageUnsupported`, string `recipe_on_device_language_note`); it all changes the moment the language does. Android: `GeminiNanoRecipeModel.SUPPORTED_LANGUAGES`, English only until another language has been tried on real phones (ML Kit gives no per-language check; don't widen it on documentation alone), and the model is downloaded only while the language is one it writes. iOS asks `SystemLanguageModel.supportsLocale` afresh on every check (`FoundationModelsRecipeModel.availability(for:)`, rule `OnDeviceRecipeAvailability.of`, checked by `iosApp/RecipeConfigCheck/check.sh`): today en, de, es, fr, it, and from iOS 26.1 nb, sv, da; never ru, pl, uk. A write already running finishes in the language it started with.
- **Free recipes for signing in** (owner's decisions 2026-11-16; spec decisions and design in `docs/design/src/pages/welcome.html` and `docs/design/brief.md`; backend "welcome grant", `functions/README.md` "Welcome grant"): someone who signs in with Google or Apple gets a few free recipes, once per Google or Apple account. How many is the server's (`config/runtime.welcome.recipes`, 3 at launch, 0 turns it off; `perDay` brakes the grants a day). `getWelcomeOffer` (App Check, no sign-in, no input, nothing stored about the caller) says how many; it is the one call the apps make before a sign-in or a purchase, only on installs where the paid route can be available and only while signed out or not yet claimed, when the Recipe tab is shown but not more often than every 15 minutes, and once more before the sign-in sheet. The last answer shows at once; one older than a day counts as none. The hint ("Sign in and get 3 free recipes"; signed in and not claimed "Get 3 free recipes", the number from `welcomeRecipes` beside the balance) is shown only with a number above zero; with zero, no answer, a failed call or an old server nothing free is promised and sign-in stays a plain sign-in. On the Recipe form it is the first row of "Other ways" (gift tile, chevron; while claiming a spinner and "Getting your free recipes…"; in a menu set too short of recipes its line is `welcome_menu_enough` / `welcome_menu_smaller` / `welcome_menu_single`, without the number), and it is in "How recipes work", on the Buy sheet and in Recipe settings' account card, hidden while buying is paused or blocked, and animates in when the answer arrives on screen (reduced motion: a cross-fade); an open sheet never changes. Any sign-in made while an offer shows calls `claimWelcome` once: `GRANTED` (a confirmation, the balance), `ALREADY` (a dialog with "See recipe packs"), `OFF`, or not reached ("Try again"; the call is idempotent). Free recipes are spent like bought ones everywhere, the Taste profile gate included, but are never purchases (no refund allowance, not reported to Apple, never hiding the use of bought recipes). Right after a sign-in is linked to an account the apps refresh the ID token and call `getBalance` once (`recordLinkedSignIn`), because the server records each Google or Apple account it sees and Firebase tells it nothing about a link or an unlink. One rule on both platforms: `shared/.../recipe/WelcomeRecipes.kt` and iOS `Recipe/WelcomeRecipes.swift` (checked by `iosApp/RecipeConfigCheck/check.sh`). Debug demo: Android `--ei demoWelcome <n>`, `--es demoWelcomeAccount signedIn|onPhone`, `--ez demoWelcomeClaimed`, `--ei demoWelcomeDelay <ms>`, `--es demoWelcomeState claiming|buy|sheet|adding|failed|granted|already|off|offNow|notReached`; iOS `-demoWelcomeOffer <n>`, `-demoWelcomeDelay <s>`, `-demoWelcomeClaimed YES`, `-demoWelcomeOutcome granted|already|off|notReached`, `-demoRoute welcomeSignIn`.
- **Taste profile** (Recipe settings, a row between Language and the account card; owner's decisions 2026-11-15/16, design in `docs/design/src/pages/taste.html`): a short quiz whose questions, options, caps, grouping, icons and every text come from the server, so they change by a backend deploy, never an app release. The apps hold no question or option and no text for them, only the chrome (row, promo sheet, progress, buttons, cap and conflict lines, snackbars, loading and error). Server: the catalogue is code, `functions/src/taste/catalogue.ts` (eight languages and the fixed English words the prompt uses; `functions/test/tasteCatalogue.test.ts` fails on a missing text, and `test/fixtures/taste-ids.json` on an id whose meaning changed: an id is never reused for something else); `getTasteQuiz` serves it in the app's language (signed-in caller, nothing charged), `config/runtime.tasteQuiz.hidden` hides a step or option without a deploy, and `generateRecipe` takes `taste` as a map step id → option ids, dropping what the current quiz doesn't have instead of refusing, and binding the request id to the answers as sent (functions/CONTRACT.md "Taste profile (request)", `getTasteQuiz`). The prompt gets one fixed-wording block of soft preferences: pantry first, allergens and diets always win, "rather skip" is never an allergen; the measuring-units step (`units`: grams, cups, spoons, °C/°F...) gets its own fixed-wording UNITS block on how amounts and temperatures are written, never on what goes into a dish. Clients (one rule on both, `shared/.../recipe/TasteProfile.kt` and iOS `Recipe/TasteProfile.swift`, checked by `iosApp/RecipeConfigCheck/check.sh`): the answers stay on the device under their own key (not in `RecipeConfig`, not in the app's backup file), with the quiz version and the step ids the person has been through; the definition is cached per language and never swapped under an open quiz. What is shown and sent is the stored answers filtered through the current definition, and a definition change never rewrites or announces anything: an option hidden for a while and back is ticked again, a new question is noted as "· 1 new question" on the settings row and as a dot on the Recipe header's settings button (`tasteHasNewQuestions` / `TasteProfile.hasNewQuestions`: only for someone who can open the quiz and has steps they have not been through, a first-time buyer included; the seen step ids live under their own key apart from the answers, and clearing the profile doesn't bring the dot back), and an unreadable definition falls back to the last good cache. The apps learn of a changed quiz from `tasteQuizVersion` beside every `balance` and then fetch it quietly, once per version and language, never for the promo case and never creating an account. `taste` goes only into a paid `generateRecipe` request, when it is not empty and a reply said `acceptsTaste` (`serverTakesTaste`); never into the shared prompt or the phone's model. The gate (`tasteEntry` / `TasteProfile.entry`): hidden where packs can't be bought, where the server hasn't said `acceptsTaste`, and for a buyer blocked from buying with no recipes and no saved profile; the quiz for someone with recipes in a pack or a saved profile; otherwise the promo sheet ("See recipe packs" / "Cancel"). Opening either creates no account; the quiz is fetched only for an account that already exists. - **Pack prices** are the stores' own; nothing in the apps states one. **Barcode/OCR pipeline** (Android): `androidApp/.../camera/BarcodeAnalyzer.kt` and `TextOcrAnalyzer.kt` are CameraX `ImageAnalysis.Analyzer` implementations feeding ML Kit. A scanned barcode first goes through `GS1BarcodeParser.extractExpiryDate` (shared module) to try to pull an expiry date straight out of AI(17)/AI(15) segments before falling back to product lookup + manual/OCR date entry. `DateOcrParser.parseBestDate` (shared module) scores multiple date-format regexes per OCR line, preferring lines near a keyword (EXP, BB, BEST BEFORE, MHD, BÄST FÖRE, BEDST FØR, ГОДЕН ДО... in every app language, matched on the lower-cased line with a letter-aware boundary, not `\b`) and reading month names in every app language by their first three letters.

**The printed date with the barcode** (Barcode and Batch modes, one rule on both platforms; pure rule in `shared/.../viewmodel/BatchDateRead.kt`, state in `PantryStateHolder`, tests `BatchDateReadTest` and `androidApp`'s `BatchScanTest`): `ScanFrameAnalyzer` (`androidApp/.../camera/`) hands every frame to the barcode reader and the same frames to Date mode's `TextOcrAnalyzer` (same parser and acceptance), from a bitmap copy so the frame closes when the barcode reader is done; text recognition runs one frame at a time, every frame it can while a Batch date window is open, not at all while Barcode mode holds a scan that already has its date (until Scan again), else at most every `BACKGROUND_DATE_READ_INTERVAL_MILLIS` (300 ms; `BatchDateRead.readIntervalMillis`, `PantryStateHolder.dateReadIntervalMillis`). The analyzers' ML Kit clients are closed when the camera rebinds or goes, each once its running reads finish (`InFlightClient`). A date read with no window open is kept as the `RecentDate` for `RECENT_DATE_MILLIS` (2 s) unless it is the same day as the date that last landed on a product (`BatchDateRead.keepsAsRecent`: that pack is usually still in view; a GS1 date in a scanned barcode counts as landed; replaced by each landing, kept by Undo and by Scan again); a read inside an open window (normal or rescan) that doesn't land is never kept. Committing the queue, a mode change and the scanner opening or closing close any window and clear both (`forgetScanDates`); Scan again clears only the recent date (`forgetRecentDate`). Barcode mode (`onBarcodeScanned`, `onScanDateRead`): a GS1 date wins, else a recent date is the scan's detected date (`PantryUiState.detectedDateReadOffPack` for the "from the packaging" caption), and a date read while the scan is held with no date yet fills it once; Scan date's explicit read still replaces it, and the add form's date stays editable. Batch mode (`enqueueBatchScan`, `onBatchDateRead`): every scan (new row or a repeat that bumps one) uses up the recent date; when `BatchDateRead.mayTake` holds for the row (row queued, not a receipt row, not DETECTED, date not set by hand: `BatchScanEntry.dateSetByHand`, set by `updateBatchEntry` when the date changes) a recent date lands at once, else a 10-second `BatchDateWindow` (`BATCH_DATE_WINDOW_MILLIS`) opens for it, replacing any open one, and the first read lands as DETECTED and closes it; a row that can't take a date opens no window and closes the last one. Tapping a queued row's date (`batch_date_rescan`; `BatchDateRead.mayRescan`: not a receipt row, not looking up) opens a rescan window (`startBatchDateRescan`): the next read that differs from the row's date replaces it whatever its source, a same-day read is ignored with the window left open, the recent date is never used, the aim hint is Date mode's and the row has the selected fill; a barcode scan ends it. A product lookup still in flight keeps the read date and only becomes what Undo goes back to (`withLookupSuggestion`, `BatchScanEntry.dateBeforeRead`). Each landing on a Batch row shows "Date read: {date}" (`batch_date_read`) with Undo (`undoBatchDateRead`: date and source as before, one level, window left closed). Time comes from the state holder's injectable `nowMillis`. iOS has a hand-kept twin: `BatchDateRead` in `iosApp/FoodTracker/Models/BatchScanEntry.swift`, state in `NativePantryViewModel` (`batchDateWindow`, `applyBatchDateRead`, `undoBatchDateRead`, `closeBatchDateWindow()`), camera in `Scanner/CameraScannerView.swift`, checked by `iosApp/BatchDateReadCheck/check.sh` (not run by CI).
